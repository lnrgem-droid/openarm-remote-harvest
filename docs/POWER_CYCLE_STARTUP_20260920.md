# 机械臂断电重上电后“假 RUNNING”的启动修复

## 原因与现场证据

2026-09-20：主机与 Jetson 的控制进程在机械臂断电期间没有退出。
重新上电后仍能收到位置反馈，网关继续显示 RUNNING / FOLLOW / fault_bits=0，
但对四条 CAN 总线的被动读取确认 32 个电机反馈状态码全部为 0（未使能）。
旧界面启动脚本只检查软件状态、反馈新鲜度和位置误差，因此复用旧栈而没有重新初始化。
即使误差小于 0.20 rad，或者主从完全重合，也不能据此证明驱动已使能。

## 修改范围

- `scripts/check_motor_enable.py`：仅接收 CAN，不发送报文；同时检查两根主臂和两根从臂的全部 32 个驱动，包括夹爪。
  每端监听 0.75 秒，每个电机至少 3 帧、最后一帧不超过 250 ms，状态码必须一致。
  不把 CAN FD flags 当成电机状态。缺帧、旧帧、混合状态和故障码均不视为已使能。
  Jetson 检查通过 SSH 发送同一份只读脚本执行，无需安装 Python 依赖或编译控制器。
- `daily_start_teleop_rgbd.sh`：只有电机全部已使能且原软件健康合同通过才能复用。
  旧栈无故障、左右 FOLLOW、无回位/过渡/录制任务且 32 个驱动全部未使能时，提供重新归位恢复入口。
  按用户后续要求，桌面点击启动即请求全自动初始化；显示 3 秒提示后继续，不再要求输入“启动”。
  另外检查录制管理器空闲，再重新检查控制和电机状态；倒计时可 Ctrl+C 取消。
  该恢复仅在用户主动再次点击启动时执行，不是后台监控自动重启。未使能也可能来自人为停止，
  所以 FAULT/E_STOP、HOLD、部分失能和录制锁仍不允许自动撤销。
  HOLD、FAULT、E_STOP、部分掉电或反馈缺失不自动归位，保留明确报错。
- `run_bimanual_remote_feedback.sh`：在打印最终启动成功之前，额外被动确认主从全部驱动已使能；不满足则退出并走原保持清理流程。
  此核心为“仅遥操”“遥操加采图”“蘑菇采集控制台”共用。

原遥操算法、J7 试调参数、重力补偿、速度限制、看门狗和录制逻辑不因本修复而改变。
本检查是启动/复用准入，不是新的运行时安全看门狗，也不能代替急停或验证实际跟随质量。

## 使用

1. 上电并等待电源稳定，确认急停按正常流程解除、路径安全且没有夹持物。
2. 双击原桌面“启动蘑菇采集控制台”。
3. 若提示旧进程仍在、32 个电机未使能，在符合恢复条件时自动重新初始化，不需输入。
4. 等待受控归位、ALIGN/RUN 和电机使能检查通过，再低速验证跟随。
5. 正常遥操时重复打开界面不应重新归位；停止录制也不停止遥操。

## 验证与边界

无硬件回归覆盖报文解析、冷/旧状态判定、缺帧/混合/故障、HOLD/录制禁止恢复、实际 Bash 分支的正常复用/自动恢复/异常拒绝，以及启动脚本语法。
现场只读探测正确识别当前 32 个驱动全部未使能，每个驱动在采样窗口内收到了数百条反馈。
本次没有主动断电、重新使能、执行归位或修改急停状态；下一次完整真机重新启动仍需现场确认并验收，不能仅以软件测试宣称已经通过。
