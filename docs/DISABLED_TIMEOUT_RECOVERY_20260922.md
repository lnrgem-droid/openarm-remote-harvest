# 重新上电后的旧超时会话恢复

## 报错与原因

现场9月22日的日志显示：主机/Jetson网络可达，32个驱动持续反馈但全部未使能。
9月20日启动的控制进程仍在，保留 `FAULT / fault_bits=1 / leader action receive timeout`。
现在收到新的动作包不等于旧故障可以自动清除。旧启动器仅支持部分无故障重上电场景，
以及Jetson重启后的空控制栈场景；本情况只报错退出，操作者只能手动重启服务。

## 修改范围

只扩展原桌面入口调用的 `scripts/daily_start_teleop_rgbd.sh` 和只读恢复分类器
`scripts/inspect_teleop_recovery.py`，不修改控制增益、超时、对齐门槛、看门狗、采集格式。
桌面“启动蘑菇采集控制台”无需替换。不发送RESET/RUN绕过控制栈完整启动流程。

新增 `DISABLED_TIMEOUT_CONFIRM`，必须同时满足：

- 安全状态为FAULT，故障位**仅为1**且原因精确为主端动作接收超时；不是E_STOP或CAN故障。
- SSH正常；主机can0/can1、Jetson can1/can2均UP、ERROR-ACTIVE、CAN FD为1M/5M。
- 被动检查32个电机，每个都有至少3个一致的失能反馈且反馈新鲜；不只信任汇总状态。
- 当前主端动作、从端反馈均新鲜（小于100ms），双臂反馈存在，控制会话身份有效。
- 独立录制器确认空闲；控制侧无录制/封装锁、无正在回位或切换任务。
- 遗留HOLD仅在上述**全部电机已失能**的条件下允许进入确认；提示明确告知旧保持任务
  会被清理，必须人工移走夹持物，不能推定失能就代表物体安全。

界面操作仍在原启动终端：显示原因后，确认夹爪已清空、四臂路径安全、急停可用，
输入 `r` 或“恢复”并回车。60秒未确认、EOF或取消时不重启、不归位。
确认后重新独立采样全部准入条件，并核对Jetson boot ID、恢复类型、主端服务PID和
主端会话ID未变化。符合才进入原启动流程：清理旧控制栈→初始化→四臂归位→对齐→RUNNING。

程序默认初始位与保存的右臂采摘位是两回事。恢复不删除已保存的采摘位，不自动续录，
不自动恢复旧左臂HOLD；新启动完成后双臂FOLLOW。需要采摘位时再明确使用回位按钮。
有使能电机、状态未知、混合使能、急停、其他故障或录制/运动任务时，不进入这个恢复分支。

## 验证边界

软件测试覆盖实际shell分支的确认/取消/二次状态变化、会话变化、重新启动分支选择；
逐电机反馈缺失、失能不一致、过期、CAN异常、其他故障、录制中均拒绝。
主机回归164项、Jetson相关回归85项通过，Bash语法和改动空白检查通过。
使用只读实机检查，当前现场状态正确分类为 `DISABLED_TIMEOUT_CONFIRM`，
且 `automatic_restart_allowed=false`。本次未替操作者确认，未驱动机械臂或实测归位。

旧进程的超时故障仍会保留，直到现场在新启动器完成明确确认；安装修复并不等于已经恢复遥操。
