# 停止后重复启动失败：失能检查点修复

2026-11-03，现场停止后主机服务已退出，从端仍保留旧控制进程。
日志显示失能后反馈停止触发 CAN_ERROR，随后退出时的 HOLD 被拒绝，
额外锁存 INVALID_COMMAND（fault_bits=10）。最终失能回执没有保存。
再次启动只能看到故障旧会话和无反馈电机，因此被正确拦截。

## 根因与修改

- 看门狗在 FAULT/E_STOP 收到 HOLD 时保留原状态、故障位及首次故障证据。
  不清故障，不恢复 RUN，也不把该回复解释成健康保持。
- 两端共 32 个电机的本次失能反馈核验通过后，立即原子写入 schema 2
  `drives_disabled` 检查点，并对文件和目录执行 fsync；随后才停止主机服务。
- 服务退出和身份复核完成后将检查点标记为 `complete`。
  后续检查失败不会删除已经得到的失能证据。
- 明确重试停止时，可依据同一启动实例、主从会话、进程身份和完整回执续做退出。
  不再次使能、归位、发送 HOLD 或要求已静默的驱动再次响应。
- 服务尚未退出时不允许启动；提示先续做停止。服务已经退出时，未完成最后标记
  的检查点也必须通过全部身份、录制、CAN、故障和新反馈检查，才允许用户明确启动。
- 启动回执在确认新服务实例后才消费；systemd 尚未创建新实例就失败时仍能重试。
- 启动预检检查实际安装看门狗的故障后 HOLD 行为，防止旧安装包再次引入该问题。
- 界面区分“失能未确认”和“失能已核验、停止流程待完成”。

## 验证

250 项相关离线测试通过，包括中断、重复请求、服务失败、身份变化、重新使能、
急停和无效命令拒绝；Shell/Python 语法检查通过。
Jetson 实际 overlay 的只读启动兼容性检查通过。
未操作电机、未重启现有会话；完整真机停止/启动循环尚未验收。

既有 schema 1 回执保持兼容。新代码不会补造修复前丢失的失能回执，
也不会依据 UNKNOWN 电机状态直接恢复旧故障会话。
