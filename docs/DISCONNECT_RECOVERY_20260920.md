# 现场断连与重新上电：恢复边界

## 原则

9月22日新增“旧动作超时故障＋32个电机全部失能”的人工确认恢复分支，详见
[重新上电后的旧超时会话恢复](DISABLED_TIMEOUT_RECOVERY_20260922.md)。
仅这类经完整检查的故障可在启动器中确认后重新初始化；仍不自动清故障或恢复运动。

通信恢复不等于允许机械臂恢复运动。新功能只做诊断和有条件的启动恢复，
不绕过看门狗、对齐、急停及电机使能检查，不自动续录旧episode。
`systemd active`仅表示主机进程仍活着，不能表示从臂已连接或已使能。

## 场景处理

| 场景 | 处理 |
|---|---|
| 正常双臂RUNNING，再打开界面 | 满足同会话验收及真实电机使能检查后复用，不重新归位 |
| 主从电脑都没重启，机械臂电源重上电 | 保留原有窄范围恢复：两端全部失能、无故障、无保持/录制/回位任务才允许启动流程重建 |
| Jetson重启，主机旧服务还在 | 新增：核实启动身份或服务寿命证据、远端无控制进程/套接字、主端全部失能、CAN FD参数正常、录制器空闲；输入“恢复”后再次核实，才重新初始化和归位 |
| 网线、交换机、UDP链路中断达到控制超时 | 保留现有从端故障/保持处理；重连不自动RESET/RUN。新增慢速只读运行诊断，不把旧成功日志当当前健康 |
| SSH不可用/IP不通 | 启动退出，明确提示网络或SSH错误；不擅自改网络、清SSH身份或驱动机械臂 |
| 控制进程崩溃，但没有Jetson重启证据 | 不冒充“正常重上电”；提示无法解释的控制栈退出，需查日志 |
| 从端只有部分控制进程存活、旧套接字存在 | 不自动杀掉重来，阻断恢复，防止两个控制者或错误覆盖现有状态 |
| CAN缺失、BUS-OFF、速率或FD配置不符 | 恢复准入失败，不靠重置安全故障掩盖CAN问题 |
| 主端只有部分电机失能、未知反馈或电机故障 | 不能按“全部已安全失能”处理，禁止上述Jetson重启恢复 |
| 正在录制/封装、左臂保持、右臂回位、急停或故障锁存 | 不自动重新归位，不解除锁存；先处理当前任务或故障 |
| 确认恢复期间再次重启、状态变化或录制启动 | 二次检查拒绝，旧确认失效 |

“控制超时后保持”依赖仍在工作的控制器、CAN和驱动。Jetson死机、控制进程被杀、
电机断电或CAN断开时，软件不能保证保持或制动；需要已有机械支撑/独立保护和现场急停。
本次没有新增或认证硬件保护，不能声称覆盖所有掉电风险。

## 本次新增代码

- `scripts/inspect_teleop_recovery.py`：只读检查和分类，绝不发CAN命令，不发RESET/RUN。
  读取Jetson boot ID、uptime、控制进程、状态套接字、CAN配置、录制状态和主机真实失能状态。
- `scripts/daily_start_teleop_rgbd.sh`：接入“恢复”确认及二次核验。提示最长等60秒；取消或无输入就退出。
  诊断证据位于主机 `/tmp/openarm-daily-start/recovery-evidence.json`。
- `scripts/run_bimanual_remote_feedback.sh`：启动前后核对Jetson boot ID，通过后记录
  `/tmp/openarm-remote-teleop/peer-boot-id`，不沿用其他启动身份的成功记录。
- `scripts/watch_teleop_link.py`：启动成功后每约3秒检查通信状态，SSH最久5秒超时；只在状态变化时打印。
  `/tmp/openarm-remote-teleop/live-health.json`记录更新时间和当前诊断。
  **这是操作者诊断，不是毫秒级看门狗**；文件过期不能当作实时状态。

本次新增恢复确认接在“蘑菇采集控制台/遥操加采图”的公共启动流程。
“仅遥操”入口原本就是明确请求重启核心；它仍会重新归位，并不是无动作检查按钮。
所有调用核心的入口下次启动都会获得boot身份核验和只读运行诊断。

## 验证与本次实际状态

使用伪造状态、shell边界替身测试网络断开/重连、Jetson重启、同启动周期进程崩溃、
CAN不就绪、混合失能、录制中、保持/回位、故障/急停、取消、确认期间再次重启与准入变化。
这些测试不会调用真实启动/停止服务。
最终验证：主机完整回归142项通过；Jetson断连恢复与电机启动相关回归42项通过；
两份启动脚本通过bash语法检查，改动通过`git diff --check`。

只读实机诊断已正确把当前状态识别为 `PEER_REBOOT_CONFIRM`：主机旧会话寿命大于Jetson本次开机时长，
远端控制栈为空、CAN配置正常、录制空闲、主端全部失能。
本次没有重启遥操、重新归位或实际拔线；需要下次操作者确认后验证完整恢复运动流程。

下一次直接点击原桌面“启动蘑菇采集控制台”，看见恢复提示时，确认无夹持物且路径安全后，
输入“恢复”并回车。等待四臂归位和最终验收完成；只有新的RUNNING就绪提示出现后再遥操。
没有明确的恢复提示时，不要反复点击或手工清故障来绕过检查。

## 恢复确认提示修正

原先确认超时、输入结束（EOF）、输入不匹配都会落入同一条“已有控制栈但健康检查未通过”，
因此单凭旧日志无法判断具体是哪一种；不能据此认定又发生了CAN故障。
现在提示明确区分确认取消、输入不可读取、等待超时/中断、二次检查条件变化和再次重启。
取消后直接退出，不再用大量电机状态覆盖取消原因。

点击桌面启动器，看见“等待你的确认”后，确认无夹持物、四臂路径安全且急停可用，
点击终端输入小写 `r`（也支持 `R` 或“恢复”）并回车，须在60秒内完成。
收到确认不等于可以遥操：还要等待二次核验、归位、对齐和新的RUNNING就绪提示。
如果已显示“按 Enter 关闭此窗口”，本次启动已经结束，须关闭后重新打开，不能在此处输入恢复来继续。

新增无硬件回归覆盖空输入、EOF、超时、中文/英文确认、二次检查变化和取消分支。
使用伪终端模拟桌面启动器的 `bash ... 2>&1 | tee ...` 管道，确认输入能传递；
没有证据表明日志管道本身阻断了输入。本次未重新归位或进行实机运动测试。
