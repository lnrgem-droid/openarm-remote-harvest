# 遥操恢复：真实电机使能与操作就绪检查

日期：2026-09-23

## 本次修复的问题

电机断电重上电后，主机控制进程可能保留旧会话的 RUNNING；关节反馈仍能更新，并不代表电机已使能。此前启动阶段有物理使能检查，但运行中的界面主要依据控制器 RUNNING，因此可能显示可以遥操而实际不跟随。

本次不修改控制增益、归位目标、夹爪反馈算法或独立安全看门狗；修复启动复用、运行状态显示和录制准入所使用的统一健康判断。

## 新的判断依据

新增 `scripts/teleop_readiness.py`，启动器、后台健康监测和采集控制台共用：

- 主机 can0/can1 与 Jetson can1/can2 的全部 32 个电机（包含四个夹爪）都必须有新鲜反馈，明确返回使能状态 1。
- 逐电机验证，不能只相信汇总字段 ENABLED。失能、故障、缺失、混合或过期反馈都不能通过。
- 被动读取 CAN，不发送电机控制命令；使用内核接收时间戳排除队列中积压的旧反馈。
- 同时验证当前主臂会话、无故障、两臂启用、跟随参考已建立、动作与控制反馈新鲜，以及每臂 FOLLOW/HOLD/RETURNING 状态。
- 报告绑定主机启动 ID 和当前主臂会话；从采样开始计算有效期（4 秒），过期或监测进程退出后不得继续显示可遥操。
- 将原始 `control_state` 与 `teleop_ready` 分开。原始控制器仍可能报告 RUNNING，但它单独不再作为界面/启动复用的成功依据。
- HOLD 或 RETURNING 不能冒充该臂正在跟随。

## 恢复行为

运行会话中发现明确的电机失能或故障（包括同一采样窗内失能后又使能），该会话会立即被标记无效。电机重新上电或重新使能后，不能仅凭旧 RUNNING 自动恢复界面就绪；需要经过重新初始化的新会话。

2026-10-03 修正：单次被动诊断反馈未知不再立即永久锁定。未知期间立即禁止宣布可遥操，连续三次诊断失败才锁存；短暂未知消失后，须同会话连续三次完整健康样本才恢复操作就绪。此过程只复查状态，不发送恢复、使能或运动命令。明确失能/故障以及控制器 FAULT/E_STOP 不能走此复查路径，也不能被另一电机的未知反馈掩盖。首次锁存的原因、时间与采样证据会写入健康报告；重启监测仍保留旧锁存，历史版本未保留首因的记录会标明原因未知。

若当前 32 电机均已使能、控制与 CAN 正常，但仍有历史健康锁定，桌面启动器会检查录制已停止、左右臂均 FOLLOW、无保持/回位/过渡任务后，提示现场输入 `恢复` 或 `r`。确认后再次核对控制会话、服务实例、Jetson 身份与恢复条件，才执行原有四臂初始化、归位、对齐流程。取消、超时、EOF 或二次证据变化都会退出。不会删除历史锁定伪造恢复，也不会因重复打开窗口自动归位。

启动失败现在直接显示健康拒绝原因及证据路径，只有确实未通过对齐验收才报告对齐问题。录制器已停止且没有活动片段/收尾任务时，上次 episode 留下的 `error` 阶段允许进入确认恢复；该判定不代表上次录制成功，也不删除其错误记录。

桌面启动器检测到全部电机失能的旧控制栈时，不再倒计时自动归位。现场确认夹爪无物、路径清空、急停可用后，按提示输入 `恢复` 或 `r` 才会继续原有初始化、归位、对齐流程；取消或超时不会自动运动。混合使能、真实电机故障和未知状态不得盲目清故障或反复归位。

采集界面在健康检查不通过时拒绝开始新 episode，并显示原因；既有录制沿用遥操失效保护结束本条。停止与保存数据仍不主动停止机械臂。

## 实现位置

- `scripts/check_motor_enable.py`：被动 CAN 使能状态与接收时间验证。
- `scripts/teleop_readiness.py`：共享健康合同、会话失效标记及报告有效期。
- `scripts/watch_teleop_link.py`：主机与 Jetson 并行检查、单写入者和原子状态报告；随控制监督进程退出。
- `scripts/check_remote_running_status.py`：增加物理健康报告准入。
- `scripts/run_bimanual_remote_feedback.sh`：完成物理健康检查后才宣布启动成功。
- `scripts/daily_start_teleop_rgbd.sh`：旧会话复用和断电恢复准入。
- 相机仓库 `scripts/mushroom_collection_console.py`：动态读取健康报告、显示真实可操作状态并限制录制按钮。

运行报告：`/tmp/openarm-remote-teleop/live-health.json`。

## 验证与边界

软件回归覆盖：RUNNING 但全部失能、单电机失能、夹爪故障、反馈缺失/陈旧、错误会话、旧报告、会话恢复锁定、界面按钮和启动复用拒绝、归位确认取消等。

在线检查只读取真实 CAN 与控制状态：全部 32 电机已使能；两臂为 FOLLOW。优化后一次并行检查约 1.1–1.3 秒；连续 24 次读取健康报告均为 READY，未过期。未为此故意断电、清除驱动故障、启动归位或重启控制栈。只更新了只读监测进程和空闲采集窗口。

此监测是秒级操作就绪诊断，**不是毫秒级安全看门狗、急停或物理失效保护**，也不会发出保持/失能命令。底层原始 RUNNING 字段并未改成驱动状态。绕过这些入口的其他程序必须自行采用相同准入合同，不能只判断字符串 RUNNING。

实际冷启动、断电恢复后的归位与跟随仍需下次现场验收；本次没有用软件模拟结果冒充断电真机测试。代码没有在本次自动提交或推送 GitHub。
