# 采集控制台：机械臂下电

桌面“启动蘑菇采集控制台”对应的界面右上角新增“机械臂下电…”。
普通关闭窗口、结束采集会话继续沿用原行为，不触发电机失能。

操作前放下夹持物，并安置、支撑主从四臂。确认后依次完成：

1. 查询真实录制状态；正在录制的条目标记中止，正在封装的条目保留原结果。
2. 等待同一条目的封装结果，核对录制退出码与 RGB-D 完整写入回执。
3. 停止跟随和正在执行的右臂回位，并重新读取控制状态确认。
4. 主机与 Jetson 都先打开被动 CAN 监听，再分别调用已有 ROS 电机失能服务。
5. 要求主从全部 32 个电机在失能命令发出后各收到连续三条失能反馈；没有反馈不是失能证据。
6. 确认失能后停止主机遥操服务；核对服务不再运行且没有剩余进程组。

Jetson、相机、录制管理器保持运行。界面不会切断硬件供电，也不会关机、重新使能或归位。
再次使用机械臂需通过原桌面启动及恢复流程；启动可能归位。

## 正常下电后再次启动

下电结束时保存 `~/.local/state/openarm/last-power-down.json`，包含全部 32 个电机的
失能回执、两端系统启动标识、遥操服务实例、从端进程启动标识和控制会话标识。
Jetson 上的旧网关在电机停止反馈后可能显示 CAN 故障；单凭这个状态不应清故障或归位。

原桌面启动器现在会核对上述正常下电记录。只有同一旧会话、主机遥操服务已停止、
录制空闲、CAN 接口正常且没有新的使能/电机故障反馈时，才显示“正常下电后恢复”确认。
操作者确认无夹持物、四臂路径清空后，输入 `r` 或 `恢复` 并回车；程序二次核对身份和
状态后消费这条记录，再执行原有初始化、归位、对齐流程。取消或超时不产生运动。
记录缺失、已消费、控制进程更换或会话变化，都不能用于放行未知故障。

2026-10-01 补充修复：首次版本漏接了该恢复入口，导致完成下电后再次启动被旧 FAULT
状态拦截。现已补上持久化回执和确认恢复流程，并以当次真实验收日志恢复了仍然相同的
旧会话回执；未通过把 UNKNOWN 当作失能、忽略所有 CAN 故障或强制重启来修复。

## 失败处理

保存失败、状态未知或等待超时会阻止后续失能。失能失败或反馈不全会分别列出两端结果，
不会显示全部成功。允许再次点击下电，但不会使用旧的失能反馈证明新操作成功；若已失能
电机停止反馈或服务已退出，重试可能仍报告未确认，需要现场核实，不得为“通过检查”自动上电。
下电开始后本窗口的录制和姿态操作锁定；等待结果期间不能关闭窗口。

协调器为 `scripts/power_down_arms.py`，JSON 行协议事件为 `progress`、`device_result`、`complete`。
直接调用必须显式传入 `--confirm`，表示已完成四臂支撑确认。GUI 在确认弹窗后才传入此参数。
远端执行当前主机脚本的受限工作函数，无需更换 Jetson 控制栈或重新编译电机控制器。

## 验证（2026-10-01）

- 模拟测试覆盖保存、互锁、反馈缺失、部分失败、状态延迟和服务停止状态。
- 用户明确确认现场安全后，实机空闲下电已捕获两端全部 32 个电机各三条失能反馈。
- 修复现场发现的两个判定问题：HOLD 即时回复可能含旧状态，须重新读状态确认；正常停止的
  shell 退出码 143 会使 systemd 标记 failed，需结合 MainPID=0 和空 ControlGroup 判断已停止。
- 修正后独立复验服务停止检查通过；Jetson 仍在线，录制器空闲，三路相机健康。
- 实机测试没有开始新录制，没有重新使能或归位。录制中/封装中下电由模拟测试覆盖。
